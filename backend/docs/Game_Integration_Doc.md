# **Game Integration Guide**

## **1\. Purpose**

This document describes how a third-party game can be integrated into the BanditGames platform. It explains the technical onboarding process, required API interactions, optional achievement support, and the approval lifecycle. **No Platform SDK** is used; integration is performed via HTTP APIs.

The target audience is external game developers who want to publish their game on the platform.

---

## **2\. High-level Integration Flow**

1. **Game submission** via the public developer API (`/api/dev/games`)  
2. **Manual approval** by a platform administrator  
3. **Game availability** on the platform after approval  
4. *(Optional)* **Achievement integration** using platform-defined event contracts

Only approved games may appear on the platform or publish achievement events.

---

## **3\. Submitting a Game to the Platform**

### **3.1 Endpoint**

**POST** `/api/dev/games`

This endpoint is publicly accessible to game developers and is used to register a new game with the platform.

---

### **3.2 Request Payload**

{  
  "name": "Chess",  
  "description": "Classic chess game",  
  "rules": "Standard FIDE rules",  
  "pictureUrl": "https://example.com/chess.png",  
  "urlGameSession": "http://localhost:3000/game",  
  "availableAchievements": \[  
    {  
      "code": "FIRST BLOOD",  
      "description": "Capture your opponent's first piece"  
    }  
  \]  
}

#### **Field description**

| Field | Required | Description |
| ----- | ----- | ----- |
| `name` | Yes | Display name of the game |
| `description` | Yes | Short functional description |
| `rules` | Yes | Game rules shown on the platform |
| `pictureUrl` | Yes | Public image used by the platform |
| `urlGameSession` | Yes | URL where the game can be played |
| `availableAchievements` | No | Optional list of achievements supported by the game |

If `availableAchievements` is omitted or empty, the game will be registered **without achievements**.

---

### **3.3 URL Parameters**

In order for ease of integration with our platform and for advanced features such as the ability for our platform to track statistics about the game and for players to unlock achievements, it is suggested that the url conforms to the following structure:

{backend url}/{game}?sessionId={}\&playerId={}

The parameters will be included in the url from the lobby when the players are redirected to the game.

---

### **3.4 Achievements at Submission Time (Optional)**

Achievements are defined **declaratively** during game submission using a human-readable title (`code`) and a human-readable description.

Important:

Achievement **IDs are generated by the platform**, not by the game. The platform developer will share the unique IDs of each achievement to the game developer after the game has been approved and added to the platform.

---

**3.5 Events accepted by the platform**  
The events that are currently accepted by the platform are:

- CreatedGameEvent  
- GameResultEvent  
- MoveMadeEvent

The game developer’s free to structure those events as they will, although they will be provided with a certain structure making the integration process easier after their game is approved.

---

## **4\. Game Approval Lifecycle**

After submission:

1. The game is stored in a **PENDING** state  
2. A platform administrator reviews the submission  
3. The administrator either:  
   * **Approves** the game → game becomes active  
   * **Rejects** the game → game is not published

Only **approved games** may:

* Appear on the platform  
* Publish achievement-related events

---

## **5\. Achievement Integration (Optional)**

Achievement integration is **opt-in** and only relevant if `availableAchievements` were provided during submission.

### **5.1 Achievement Unlock Events**

When a player satisfies the criteria for unlocking an achievement, the game must publish an event to the platform.

#### **Event semantics**

* One event per unlocked achievement  
* Event is idempotent  
* Platform determines whether the achievement was already unlocked or not.

#### **Required data**

| Field | Description |
| ----- | ----- |
| `achievementId` | Unique achievement identifier assigned after approval |
| `playerId` | Platform-wide player identifier |

---

### **5.2 Example Achievement Event**

{  
  "achievementId": "uuid",  
  "playerId": "uuid"  
}

---

## **6\. Messaging Infrastructure**

### **6.1 Shared Achievement Queue**

The platform exposes a **generic achievement event queue** that can be used by **all approved games**.

* Queue name (example): `platform.achievement.unlocked`  
* All games publish to the same queue  
* Events are distinguished by `achievementId`

This avoids the need for per-game RabbitMQ configuration.

---

### **6.2 Routing Rules**

* Only approved games may publish events with valid achievementId & playerId  
* Payloads must conform to the documented JSON contract

---

## **8\. Summary**

* Games are onboarded via a **single public REST endpoint**  
* Achievements are **optional** and defined declaratively  
* Games reference achievements by ID provided by platform admin  
* Achievement unlocking is event-driven  
* One shared achievement queue is used for all games  
* Admin approval is mandatory before activation

This approach ensures ease of addition, extensibility, and long-term maintainability of the platform.

Other event integration is available in order to publish game states, but for a simple integration process, the above describes all that is necessary with the optional addition of achievements.
